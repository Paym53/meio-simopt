# Deploying the web API on Render (runbook)

The deployment is defined as code in [`render.yaml`](../render.yaml) (a Render *Blueprint*).
`tests/test_deployment.py` keeps it consistent with `api.py` and CI. Change settings in
`render.yaml` and let Render sync them, rather than clicking them in the dashboard, so the
repository stays the single source of truth.

## What is configured and why

| Setting | Value | Reason |
|---|---|---|
| Plan | `free` | Costs nothing to start. See "Choosing the plan" below. |
| Region | `frankfurt` | Cannot be changed later: pick the region of your Supabase project before the first deploy. |
| Branch | `main` | Deploys only reviewed, merged code. |
| Auto-deploy | `checksPass` | A commit on `main` is deployed only after the GitHub Actions tests pass. |
| Start command | `uvicorn api:app ... --workers 1` | The run registry and the one-run-at-a-time lock live in memory: one process only. |
| Health check | `/health` | Render only switches traffic to a new deploy that answers it (zero-downtime deploys on paid plans). |
| `PYTHON_VERSION` | `3.11.9` | Same as CI. |
| `MEIO_API_KEY` | generated by Render | Every endpoint except `/health` needs the header `X-API-Key`. |
| `MEIO_ALLOWED_PRESETS` | `quick,standard` | Measured peak memory: quick 176 MB, standard 266 MB, full 446 MB (+ about 90 MB for the server). `full` is too close to 512 MB. |
| `MEIO_OUTPUT_DIR` | `/tmp/meio-output` | Run folders. Render's disk is ephemeral: they are lost at every deploy, restart or spin-down. |

## Choosing the plan

A `quick` run needs about 100 CPU-seconds (single-threaded; measured on a development machine,
Render's CPUs may be slower).

| Plan | CPU / RAM | Expected `quick` run | Behaviour |
|---|---|---|---|
| Free | 0.1 CPU / 512 MB | ~15-20 min | Sleeps after 15 min without requests (first request then waits ~1 min); monthly free hours are limited |
| Starter (paid) | 0.5 CPU / 512 MB | ~3-4 min | Always on |

Use Free to try the integration; use Starter (or larger) once people rely on it.
Plan details change: check render.com/pricing before deciding.

## Step by step

1. **Merge to `main`.** The Blueprint deploys `main`; the API must be merged first (pull request).
2. **Render account.** Sign up at render.com with GitHub. When Render asks for GitHub access,
   choose *Only select repositories* and pick `meio-simopt` (least privilege).
3. **Region.** Look up your Supabase project's region (Supabase dashboard -> Project settings).
   If it is not in Europe, change `region:` in `render.yaml` (oregon, ohio, virginia, frankfurt,
   singapore) and merge that first.
4. **Create from the Blueprint.** Dashboard -> *New* -> *Blueprint* -> select `meio-simopt`.
   Render shows the service from `render.yaml`. Check name, plan and region, then *Apply*.
5. **Watch the first deploy.** Service -> *Events* / *Logs*: the build installs
   `requirements.txt`, then the log shows `Uvicorn running on http://0.0.0.0:...` and the deploy
   turns *Live* once `/health` answers.
6. **Read the API key.** Service -> *Environment* -> `MEIO_API_KEY` -> reveal. Store it in a password
   manager. Never commit it or put it in frontend code.
7. **Smoke test** from your machine:
   ```bash
   python scripts/smoke_test.py https://<your-service>.onrender.com --key <MEIO_API_KEY>
   ```
   It checks health, key enforcement, input validation, a full `quick` run and the Excel download.
8. **Connect Lovable / Supabase.** Store `MEIO_API_URL` (the `.onrender.com` URL) and `MEIO_API_KEY`
   as Supabase secrets. Only a Supabase edge function calls the API (the key never reaches the
   browser). The edge function should save the `summary` in a Supabase table as soon as a run is
   completed, because Render's disk is not permanent.
9. **Notifications.** Account settings -> *Notifications*: e-mail on failed deploys.

## Operating it

- **Deploy:** merge to `main`. Render waits for the GitHub tests, then deploys.
- **Roll back:** service -> *Events* -> an earlier deploy -> *Rollback*.
- **Rotate the key:** *Environment* -> set a new `MEIO_API_KEY` -> *Save, rebuild and deploy*, then
  update the Supabase secret. Running runs are lost on redeploy; rotate when no run is active.
- **Logs:** service -> *Logs* (every run prints its full console report).
- **Polling:** the edge function should poll `GET /runs/{id}` every 10-30 s. Polling also keeps a
  free instance awake while a run is going.
- **Known limits:** one run at a time (others queue); runs and the job list are lost on restart or
  redeploy; the in-memory design needs exactly one instance. Persistent storage (database + object
  storage) and a job queue are the next step if several users run in parallel.
